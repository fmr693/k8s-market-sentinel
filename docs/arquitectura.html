Aclaración

Es la única parte que no controlas: pueden cambiar el formato, meter huecos o dejar de responder sin avisar.

Por eso cada fuente vive en su propio trabajo separado. Si CEFConnect se cae una noche, los precios y la macro entran igual: el fallo queda acotado a una pieza.

Kubernetes — el clústerdentro · desechable

Carril lento

7 CronJobs entre las 16:45 y las 23:45. Uno por fuente, más el de calidad. Grano diario.

Carril rápido

El poller: un proceso vivo que pide velas de 1 minuto cada 75 s mientras la bolsa está abierta.

Los trabajadores del carril lento son pods efímeros: nacen a su hora, piden, limpian, guardan y mueren. No conservan nada entre ejecuciones.

Aclaración

Kubernetes no sabe que Neon existe. Solo arranca contenedores a su hora y les entrega la dirección de la base en un sobre cerrado que nunca abre.

Quien habla con la base de datos es el código Python de dentro. Kubernetes se limita a que alguien fiche puntual y, si se desmaya, a mandar a otro.

Aclaración

Neon no es un bucket. Un bucket guarda ficheros y no sabe qué hay dentro; esto es una base de datos que entiende su contenido y sabe operar con él.

Por eso aquí no hace falta Spark ni ningún motor aparte: el cálculo más pesado del proyecto —el z-score sobre 252 sesiones— son 25 líneas de SQL sobre 424.000 filas. Postgres las resuelve en milisegundos.

Eso tiene dos consecuencias buenas: entra con un usuario de solo lectura —no puede romper lo que enseña, aunque permita escribir SQL clicando— y podrías cambiarlo por otra herramienta sin perder una sola regla de negocio.

El andamiaje

Tres sistemas que no tocan el dato de mercado, pero sin los cuales nada de lo anterior se sostendría. Cada uno responde a una pregunta distinta.

De dónde sale el código que se ejecuta

Los pods nacen vacíos. Alguien tiene que darles un cuerpo.

GitHub Actions al etiquetar v* GHCR docker pull Pod

Por qué así: una sola imagen contiene todos los comandos —poller, los seis ingestores y el runner de calidad—. Kubernetes elige qué cara ejecutar al arrancar cada pod. Así el código y el esquema de la base viajan siempre juntos, sin piezas descompasadas de versión.

Quién decide qué debe estar corriendo

Sin esto, lo que corre es «lo último que aplicó alguien». Nadie sabe qué, ni cuándo.

git (repositorio) vigila ArgoCD corrige El clúster

Por qué así: el repositorio deja de ser documentación de lo que hay y pasa a ser lo que hay. Desplegar se convierte en hacer un commit, y si alguien toca algo a mano en el clúster, ArgoCD lo revierte solo.
Su límite: garantiza que los objetos del clúster coincidan con git — no que un proceso ya arrancado relea su configuración. Un pod vivo conserva las variables que recibió al nacer.

Quién vigila que todo esto funcione

Los datos pueden parecer correctos mientras el sistema está roto: el dato viejo sigue ahí.

Poller /metrics Prometheus
CronJobs empujan al morir Pushgateway recoge Prometheus

Por qué dos caminos: Prometheus funciona preguntando cada pocos segundos. Al poller le da tiempo a contestar porque está vivo; los CronJobs viven treinta segundos y morirían antes de que les preguntara. Por eso ellos dejan el recado en un buzón y Prometheus lo recoge cuando pasa.

Referencia rápida: quién corre y cuándo

Horarios en Europe/Madrid, declarados en los manifiestos. Una ejecución perdida no se recupera, pero da igual: el backfill idempotente tapa el hueco en la siguiente.

La imagen es tonta y el clúster es listo.

El código Python apenas calcula; el SQL hace el trabajo intelectual; y Kubernetes no entiende nada de finanzas — solo se asegura de que los obreros fichen a su hora. El clúster es desechable, Neon es la memoria, y git es la verdad.
